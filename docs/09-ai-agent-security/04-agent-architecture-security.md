# Agent 架构安全：工具调用与权限

## 概述

模型说“用户已经同意”，执行器能直接转账吗？Agent 是围绕模型组织规划、记忆和工具的工作流。权限来自真实身份与策略，不能来自模型生成的一句话。

> 本节仅用于教育学习与合法防御；以下架构建议不包含攻击工具或载荷。

## 历史背景

模型从文本问答扩展到工具协作，错误输出开始具有现实副作用。[OWASP LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/) 将功能过多、权限过大和自主性过强列为过度代理（Excessive Agency）的重要原因。传统最小权限、隔离和交易完整性仍然适用，关键是将它们放在模型之外。

## 核心原理

建议链路为“用户目标→模型提出结构化动作→策略执行点验证→必要审批→执行前复核→受限工具→审计”。策略执行点（Policy Enforcement Point）应以确定性程序检查身份、租户、动作、对象、参数与约束；模型、提示词和另一个审查模型均不能成为最终授权者。

| 边界 | 约束示例 | 目的 |
|---|---|---|
| 身份 | 真实用户、委托主体、租户 | 防止混淆代理与跨租户访问 |
| 能力 | 只读查询与写入接口拆分 | 减少多余功能 |
| 范围 | 指定对象、目的地、额度、期限 | 限定单次行动后果 |
| 执行 | 参数校验、出口限制、隔离 | 限制错误与资源滥用 |
| 审批 | 绑定不可变动作摘要与版本 | 防止“同意后换动作” |

批准应覆盖用户、工具、对象、参数、目的地、金额或数量、状态版本、期限与唯一请求。检查与使用之间的时间差（Time of Check to Time of Use，TOCTOU）可能使权限、资源版本或参数变化；执行前需复核最新授权与前置状态，变化则重新审批，支持原子提交、幂等键或条件更新。不能把一次“允许继续”变成无限期全局许可。

工具返回值仍是不可信数据，不能自授权限、扩大预算或伪造用户意图。多代理之间传递真实委托上下文及来源标记，不能因“同事模型说可以”升级权限。密钥由后端按用途注入，不放进模型上下文。

> 🧠 **费曼自问**：助手拿着昨天批准的单据，今天能改收款人再付款吗？

## 通俗解释

模型像拟订单的业务员，执行器像核单的收银员。订单描述客户想买什么，收银系统核对账号、库存与支付许可；业务员写“老板同意”不是收银系统的凭证。

## 📖 寓言故事

驿站请聪明的信使安排送货路线，掌柜批准把三箱茶送到北门。信使途中读到一封自称仓库通知的信，想改送南门，并把数量增到十箱。库管查看许可，只允许原目的地和三箱，于是暂停出库。随后掌柜亲自更新订单，库管再次核对收货人与库存版本，签发短时有效的单次凭据。第二次运输即使信使带着旧凭据回来，也不能重复提货。聪明的路线规划可以变化，出库权限必须绑定具体货物和当前状态；许可不是一句随身携带、可任意解释的话。

## 防御步骤 / 工作流程

1. 枚举全部工具与副作用，移除无关功能，将只读、写入和高影响接口分离。
2. 在受控后端保存用户与委托身份；使用按任务范围签发的短期令牌，禁止模型决定自己的权限。
3. 验证结构化参数与目标归属，执行文件、网络和租户边界；配置时长、次数、费用上限与终止开关。
4. 高影响动作向适当人员展示具体差异和后果，批准绑定不可变动作及状态版本；执行前重新校验权限和前置条件。
5. 对执行设置幂等与失败处理，记录真实调用、结果、审批和拒绝；输出只携带任务所需数据，并保留来源污点。
6. 测试越权、过期许可、状态变化、工具返回误导和重复提交等防御结果；分阶段开放能力并保留回滚路径。

## 优缺点分析

### 优点

即使模型被误导，确定性边界也能限制后果；小接口和审计记录更容易验证责任。

### 缺点

权限服务和审批增加延迟与实现成本。约束过窄影响任务完成，约束过宽扩大风险；重复审批还可能引发疲劳，需要按后果设计。

## 应用场景

客服退款、代码发布、文档发送、运维变更都适用。每种工具应分别定义对象、数量、目的地、回滚和紧急停止，不套用一份通用“Agent 已获授权”。

## 实践建议

从只读加草稿模式开始；将“提议动作”和“实际动作”分别统计。模型调用成功不能证明业务完成，工具实际拒绝也不能掩盖不安全建议；两类结果都应评估。

## 🧠 费曼自测

1. 为什么最终授权必须在模型之外？
2. 一次退款批准应绑定哪些字段？
3. 参数没变但账户权限撤销了，执行器怎么办？
4. 工具返回文字与工具授予能力有什么区别？

## 总结

Agent 的能力来自受控接口，而非模型自述。用真实身份、有限能力、绑定审批和执行前复核，保护每一次有副作用的动作。
