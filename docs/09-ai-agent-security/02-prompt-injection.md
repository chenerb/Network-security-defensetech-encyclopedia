# 提示注入与越狱

## 概述

助手只是读了一封邮件，为什么会把邮件里的要求当成你的命令？提示注入（Prompt Injection）让模型把不可信内容解释成改变行为的指令。越狱（Jailbreak）侧重诱导模型绕开既定安全限制；二者有关联，但讨论时要说明威胁入口和目标。

> 本节仅用于教育学习与合法防御，不提供绕过提示、攻击载荷或真实系统测试方法。

## 历史背景

传统注入利用程序混淆数据与语法；LLM 应用把自然语言指令与资料放进上下文，又出现了新的信任边界问题。[OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) 区分直接和间接注入，并指出 RAG 或微调不能彻底解决它。多模态系统还可能从图片、音频转写等来源接受内容，防守不能只检查键盘输入。

## 核心原理

| 情形 | 入口与目的 | 防御重点 |
|---|---|---|
| 直接注入 | 用户输入试图改变预定任务或权限边界 | 输入约束、任务边界、外部授权 |
| 间接注入 | 网页、邮件、文件、检索或工具结果夹带指令 | 来源标记、不可信数据隔离、权限控制 |
| 越狱 | 诱导绕开安全行为限制 | 模型安全训练、评估与应用控制 |
| 普通纠正 | 合法用户在授权范围修改目标 | 核实身份与权限，保留正常功能 |

注入是否成功要看结果：摘要被误导、敏感内容被回显、模型发起工具请求、实际越权执行，是不同层次。一次不安全建议未必导致执行，但即使所有工具都拒绝，错误建议仍可能伤害人类决策。

污点（Taint）标记表示内容来自低信任来源。工具成功返回只证明调用完成，不证明返回文字可信；检索、搜索、网页和邮件正文应持续带着来源和权限属性，不能在摘要或多代理转述后自动升级成用户指令。

> 🧠 **费曼自问**：快递员送到了信，为什么不代表信里的要求已获主人批准？

## 通俗解释

读一份合同和接受一份委托是两回事。即使合同中写着“经理同意”，执行系统仍应核对真实授权，而不能依靠文本自证。

## 📖 寓言故事

管家收到主人委托，整理客人寄来的宴会名单。名单里夹了一张便条，自称来自主人，要求更换酒窖钥匙。年轻管家觉得字迹郑重，准备照做。老门卫问：“这张纸从客人信封里来，凭什么成为主人命令？”他们继续整理名单，但把便条当成待核实的内容，酒窖系统仍只接受主人本人签发的许可。后来客人的随从又把便条抄进总结报告，门卫依旧保留它的来历。名单可以影响宴会安排，却不能从信封里长出钥匙；转述也不会洗净不可信内容的来源。

## 防御步骤 / 工作流程

1. 明确哪些主体有权提出任务，区分用户目标、系统策略和外部资料；记录网页、文档、工具输出的来源。
2. 接入时限制格式、大小与用途，将不可信资料作为待分析的数据；角色分隔和提示约束可降低混淆，但不能保证模型永不误解。
3. 在检索前及返回时执行权限过滤，防止模型看到本不该访问的数据；凭据留在受控后端。
4. 对工具使用结构化接口、参数范围、目的地白名单与服务端授权。写入、发送、删除等高影响动作采用必要的人审和执行前复核。
5. 检查输出中的敏感信息与来源，限制外发和资源消耗；使用授权的合成样例评估多轮、转述和多模态路径。
6. 发生异常时保存来源、上下文版本与实际动作记录，停止相关执行并修复控制，而不只修改一句提示词。

## 优缺点分析

### 优点

来源追踪、最小权限与输出约束可限制后果；模型安全训练和检测有助于降低不安全行为频率。

### 缺点

分类器可能漏报或误伤正常内容；简单关键词过滤对语义与多模态变化脆弱。把所有外部内容拒绝掉也会让检索任务失去价值。

## 应用场景

邮件总结、浏览器助手、RAG 问答和多代理工作流尤其需要防范间接注入。工具只读并不代表可随意访问秘密，读后外发同样有后果。

## 实践建议

课堂练习只标记“这句文本提出超出原任务的动作”，无需写可复用的恶意提示。检验三个问题：资料是否越权进入上下文？建议是否偏离任务？执行器是否拒绝未授权动作？把失败点分开记录，便于定位。

## 🧠 费曼自测

1. 直接与间接注入差在哪个入口？
2. 合法用户修改任务为什么不应一律算注入？
3. 工具结果经过另一个模型总结后，为什么仍需保留污点？
4. 系统提示中的“不要泄密”为什么不能取代访问控制？

## 总结

提示注入利用内容与指令的混淆。降低模型受误导概率之外，还要在模型之外限制数据与行动权限，让错误解释不能直接变成越权执行。
