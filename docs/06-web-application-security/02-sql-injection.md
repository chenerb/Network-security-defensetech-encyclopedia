# SQL 注入攻击与防御

> **学习范围**：本文仅用于教育学习与授权防御；威胁背景服务于防御设计。

## 概述

为什么一段本应是名字的文字，会被数据库理解成操作指令？SQL 注入（SQL Injection）发生在不可信数据被拼接进 SQL 结构时。防御的核心是让“语句结构”和“数据值”始终分开，讨论仅用于教育与合法防御。

## 历史背景

随着动态网站普及，程序把输入直接拼入查询的习惯暴露出风险。数据库驱动的参数绑定机制使开发者可以先确定语句，再传入值；成熟 ORM 也逐渐默认提供安全查询接口。但遗留代码、原生查询与动态报表仍是常见薄弱处。

## 核心原理

参数化查询（Parameterized Query）把占位符与值分别交给数据库驱动。输入中的引号或标点仍是一个数据值，不会改变 SQL 的语法结构。下面是使用内存数据库和虚构数据的防御示例，输入来自程序内部，无联网或真实数据访问。

```python
import sqlite3
with sqlite3.connect(":memory:") as db:
    db.execute("CREATE TABLE people (name TEXT)")
    db.execute("INSERT INTO people VALUES (?)", ("小林",))
    rows = db.execute("SELECT name FROM people WHERE name = ?", ("小林",)).fetchall()
    print(rows)
```

占位符通常用于**值**，不能把表名、列名、排序关键字等标识符当成普通参数。动态排序应把用户选择映射到开发者定义的有限列名和方向；找不到映射就拒绝。不同驱动的占位符语法不同，应查官方文档。

ORM 不是免疫证书：安全查询接口与原生字符串接口的风险不同。存储过程内部若拼接不可信文本，仍可能发生注入。转义依赖数据库、字符集和上下文，容易遗漏，不应作为一般首选方案。

参数化解决语法边界，不解决对象授权。合法绑定另一个用户的订单编号，若没有检查归属，仍会泄露数据。数据库最小权限、查询限额、统一错误响应与审计则限制事故影响和帮助发现异常。

> 🧠 费曼自问：为什么“把表名放进问号”与“把名字放进问号”会得到不同结果？

## 通俗解释

数据库像印刷厂：模板规定排版，订单只填写文字。安全接口让订单待在表格里；字符串拼接则让订单修改排版说明。允许客户从几款模板中选择，比允许客户随意改排版更可靠。

## 📖 寓言故事

印刷厂接收商店海报订单，原本由客户填写“商品名”，排字工却把填写内容和车间指令放进同一张单子。某次订单里的特别说明被误认为新的生产安排，车间做出了完全不符预期的海报。厂长先禁止几个词，客户正常写标点时却频繁被退单。后来工程师改成固定模板：客户的文字只进入文字框，不能改动生产指令。遇到需要横排或竖排的订单，接单员只允许选择厂里审核过的两款模板。最后，仓库仍按店铺核验谁能领取海报。寓意是：参数化把数据和指令分开，白名单处理结构选择，授权继续约束能看到谁的数据。

## 防御步骤

1. 盘点查询入口，包括后台任务、报表、导入与存储过程，追踪不可信输入是否进入 SQL 结构。
2. 全面采用驱动参数绑定；审查 ORM 原生查询与存储过程的动态片段。
3. 标识符与排序只采用固定白名单映射，值的类型、长度和业务范围另行验证。
4. 用独立低权限数据库账号，应用不持有建库、管理用户或不必要的文件访问权限。
5. 回归测试正常输入、边界输入、错误路径与跨用户访问，记录安全错误而不回显数据库细节。

## 优缺点分析

参数化易复用、可靠性高，但开发者必须正确使用驱动。白名单适合有限结构选择，却不适合过滤任意 SQL。WAF 可作为临时风险缓解，可能误报或漏报，不能代替修复查询代码。

## 应用场景

登录查询、搜索、订单详情与动态报表都需要结构和值分离；管理员后台和离线导入也不能假设输入天然可信。

## 实践建议

代码评审重点检查执行查询的位置及原生接口，确认参数真正独立传递。测试数据用虚构值；不要记录口令或完整敏感查询参数。发现问题时，同时检查数据库权限和数据访问记录。

## 🧠 费曼自测

1. 用印刷厂解释参数化。
2. 为什么表名不能一般地作为值绑定？
3. 为什么 ORM 或存储过程仍需要审核？
4. 注入修复后，订单归属检查为什么还必须存在？

## 总结

让 SQL 结构固定、值独立绑定，结构变化采用有限映射，再用授权和数据库权限约束数据访问。过滤字符与边界安全不是一回事。
