# 访问控制模型：DAC、MAC、RBAC 与属性规则

## 概述

“已经登录”为什么还不能下载另一位同事的工资表？访问控制（Access Control）决定主体对资源可执行哪些动作。认证得到“是谁”，授权（Authorization）判断“能做什么”；必须把对象归属和具体操作都纳入检查。

> **教育与防御边界**：本篇仅用于教育学习与合法防御，不提供越权或攻击代码。

## 历史背景

早期系统依靠用户、组和文件权限；处理敏感分级数据的系统发展出强制访问控制。组织扩大后，基于角色的访问控制（Role-Based Access Control，RBAC）把权限与岗位关联。云服务、多租户和动态协作又推动基于属性的访问控制（Attribute-Based Access Control，ABAC），这些模型常组合使用，不是必须选定唯一一种。

## 核心原理

自主访问控制（Discretionary Access Control，DAC）允许资源所有者在策略范围内分配权限，协作灵活但权限容易扩散。强制访问控制（Mandatory Access Control，MAC）由系统统一执行标签和规则，普通所有者不能自行放宽，适合严格分级。此处 MAC 是访问控制模型，不能与密码学消息认证码的同名缩写混淆。

RBAC 把用户关联到角色，把角色关联到权限，可设置角色层级、职责分离和临时任职。角色不是“管理员或普通人”两档；把每种业务组合都做成角色会造成角色爆炸。ABAC 使用主体、资源、动作和环境属性评估规则，例如“财务员工仅可在受管设备上查看本部门账单”；属性来源必须可信，否则客户端伪造部门值会破坏策略。

最小权限（Least Privilege）限制完成任务所需范围；默认拒绝（Deny by Default）使未定义路径不能放行。执行点必须位于服务端，每个请求都检查对象级、字段级及动作权限。网关通过不代表后端可省略检查；缓存、批量接口、导出任务和异步消息也要保持一致授权语义。

> **🧠 费曼自问**：一张合法员工卡，为什么不能证明你可开每一个柜子？

## 通俗解释

DAC 像屋主给客人配钥匙；MAC 像档案馆依据密级统一决定谁能开门；RBAC 像按岗位发钥匙串；ABAC 像再核对钥匙持有人、房间用途和当前条件。钥匙管理之外，还需门锁真正执行规则。

## 📖 寓言故事

工厂起初让每位车间主人自行配钥匙，赶工时钥匙借来借去，谁都记不清还在谁手里。厂长改为按维修、仓储和采购岗位发放钥匙，但有人同时兼任采购与付款，仍能独自完成不该独办的交易。管理员把审批与付款拆开，临时维修许可写明车间、任务和到期时间，并在每扇门上核对许可。一位离职员工交回工牌后，异步仓库系统却仍保留旧名单，于是管理员把所有门锁的更新纳入离职流程。权限模型只有被完整执行、及时撤销，才真正限制行动。

## 防御步骤 / 工作流程

1. 列出主体、资源、动作与数据归属，建立权限矩阵，明确跨部门、跨租户和批量访问边界。
2. 采用默认拒绝与最小权限，按岗位设计 RBAC；需要动态条件时增加可信属性规则。
3. 在服务端统一授权组件中检查请求，保证对象查询包含租户和归属条件，禁止仅隐藏按钮。
4. 为高风险操作设置职责分离、临时授权和到期回收；员工调岗、离职同步处理全部执行点。
5. 以合成账号测试允许与拒绝路径，记录拒绝、授权变更和导出操作，定期复核实际使用权限。

## 优缺点分析

集中模型便于审计与复用，角色减少逐人配置成本。代价是策略冲突、角色数量和属性可信度需要治理；权限缓存提高性能，也会延长撤销生效时间，需要定义风险可接受的时效。

## 应用场景

企业岗位管理常用 RBAC；多租户平台结合租户属性和对象权限；高敏数据使用强制标签规则。共享文档可使用 DAC，但应限制公开分享并保留拥有者变更记录。

## 实践建议

评审一条规则时把“谁、什么对象、什么动作、什么条件”写成完整句子。检查编号相邻的对象、批量导出与后台任务是否重复执行同一约束。授权不可用时，高风险操作通常应拒绝并报警，避免临时放行变为永久惯例。
