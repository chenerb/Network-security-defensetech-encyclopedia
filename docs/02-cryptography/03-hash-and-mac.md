# 哈希与消息认证码：摘要为什么不等于信任

## 概述

下载页面同时给出文件和 SHA-256 摘要，是否足以证明文件来自官方？哈希（Hash）把任意长度输入映射到固定长度摘要，适合比较内容；若文件和摘要一起被替换，比较通过也不能证明来源。

> **教育与防御边界**：本篇仅用于教育学习与合法防御，不提供破解或攻击代码。

## 历史背景

MD5 和 SHA-1 曾广泛用于摘要，随着碰撞研究进展，已不适合新的抗碰撞安全设计。SHA-2、SHA-3 提供现代选择。1997 年 RFC 2104 规范了带密钥哈希消息认证码（Hash-based Message Authentication Code，HMAC），把共享秘密加入认证过程；口令哈希则发展出专门提高猜测成本的算法。

## 核心原理

原像抗性指给定摘要难以找到相应输入；第二原像抗性指给定输入难以找另一输入有相同摘要；碰撞抗性指难以找到任意两个不同输入具有相同摘要。固定长度摘要理论上必然存在碰撞，因此“哈希指纹绝对唯一”只是过度类比。普通哈希没有秘密，任何人都能为自己的内容生成摘要。

消息认证码（Message Authentication Code，MAC）使用共享密钥验证完整性与来源；HMAC 有规定的嵌套构造，不能用随意的“密钥加消息再哈希”替代。验证端应使用成熟库的恒定时间比较，并认证明确的字节序列：字段顺序、长度和编码不同可能产生歧义。MAC 不隐藏消息，也不能向第三方区分是哪一位共享密钥者生成的。

重复发送一份有效消息，MAC 仍会通过，因此防重放还需认证时间戳、请求标识或序号，并在接收端限制时窗、维护已用标识。密码存储使用每个口令独立的盐和专用慢哈希，例如 Argon2id；快速 SHA-256 即使加盐，也无法提供同等级猜测成本。盐通常公开，额外的 pepper 才是独立保护的秘密。

## 通俗解释

普通摘要像快递重量记录，能发现某些差异；HMAC 像只有双方会写的验收暗号，暗号还绑定包裹清单。即使暗号正确，旧包裹再次送来仍要检查送货编号是否已使用。

## 📖 寓言故事

粮仓用一张重量表核对每袋粮食，账房认为“重量相同便一定来自老供应商”。骗子换了粮袋，也换了重量表，检查顺利通过。账房随后与供应商约定一套秘密验收印记，印记记住粮种、数量和交付编号。骗子不能为新粮袋造出印记，却把上周的合格粮袋和票据再送一次。守门人直到核对交付账本才发现重复。后来供应商更换了印记钥匙，旧票据按版本处理。摘要帮助比较，秘密帮助认证，交付账本帮助识别重放，三者解决的是不同问题。

## 防御步骤 / 工作流程

1. 明确需要误差检测、可信完整性还是口令验证，分别选择摘要、MAC/签名、口令哈希。
2. 对消息规定规范化编码，绑定协议版本、调用方、目标与关键业务字段，避免遗漏金额等字段。
3. 保护并轮换 MAC 密钥，使用独立用途密钥，避免所有伙伴共享同一秘密。
4. 先验证认证码，再执行业务；结合已认证的时间与请求标识实现防重放。
5. 对口令哈希参数做容量评估，保存算法版本和盐；在成功登录时逐步升级旧哈希。

## 优缺点分析

摘要简单高效，HMAC 通常比公钥签名轻量，适合服务间认证。局限是共享密钥需要保护和分发，MAC 不提供公开可验证的签名证据；慢口令哈希也需要控制并发，避免认证服务资源耗尽。

## 应用场景

备份校验使用可信清单中的摘要；Webhook 使用签名过的时间戳与 HMAC；软件发行使用数字签名；用户口令使用专用哈希。是否要“可信清单”，取决于是否担心主动篡改，而不仅是传输损坏。

## 实践建议

完整记录参与认证的字段、编码与密钥编号；日志保留失败原因分类，不保留口令。不要把 Base64 编码当作加密，不要因用了 SHA-256 就承诺来源认证。对请求去重设置存储上限和过期策略，重复操作还应检查业务幂等性。

## 总结

摘要比较内容，MAC 认证持钥者与内容，慢哈希提高口令猜测成本。把目的分清，才能避免拿一种“哈希”解决全部信任问题。
