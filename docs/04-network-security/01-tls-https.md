# TLS 与 HTTPS：保护链路，还要验证对端

## 概述

浏览器出现锁标志，网站为什么仍可能骗你？传输层安全（Transport Layer Security，TLS）保护连接中的机密性与完整性并认证对端；HTTPS 是经 TLS 传输的 HTTP。锁表示连接到相应域名的安全通道，不证明商家诚信、页面无漏洞或终端没有恶意软件。

## 历史背景

TLS 从早期 SSL 演进，2018 年 RFC 8446 定义 TLS 1.3，删减旧算法与复杂选项。RFC 9325 在 2022 年更新安全使用建议。TLS 1.2 仍可按安全配置服务兼容客户端，但 TLS 1.0/1.1 已弃用；版本、密码套件和客户端能力应一起治理。

## 核心原理

握手先协商协议参数，通过证书及握手签名证明服务端控制相应私钥，在常见的完整 TLS 1.3 证书握手中使用临时（EC）DHE 协商秘密，再派生握手与应用数据密钥。Finished 消息认证握手记录，后续数据由 AEAD 保护。公钥机制建立信任，对称加密承担大量传输；TLS 1.3 不使用静态 RSA 密钥传输。

客户端必须验证可信链、有效期、用途与目标主机名称。服务器通常只由客户端验证；双向 TLS（mTLS）进一步认证客户端证书，但仍需把证书身份映射为业务权限。前向保密与具体密钥交换模式有关，不能把所有恢复或预共享密钥配置都视为等价。

TLS 1.3 的 0-RTT 早期数据可能被重放，不能直接承载支付、修改口令等有副作用操作。HTTPS 在反向代理结束后，代理到后端的链路需另行保护。HTTP 严格传输安全（HSTS）帮助浏览器坚持 HTTPS，但首次访问与预加载策略需要单独考虑；混合内容和不安全 Cookie 仍会削弱 Web 应用。

> **🧠 费曼自问**：安全隧道把你送到了正确门牌，为什么不代表房间内的每件事都安全？

## 通俗解释

TLS 像先查门牌证件、再搭建带防拆封条的专用管道。证件要属于你要去的地点；把验证关闭，就像只检查“有管道”而不查管道通向谁。mTLS 则让两端都出示证件。

## 📖 寓言故事

邮局修建封闭滑道，信件不再被路人看见。小镇居民只看滑道是否有锁，骗子便把另一条有锁滑道接到自己的柜台。新邮员先查柜台门牌与商会证明，再封闭滑道。后来为加快早晨投递，邮局允许重复使用昨天的入场票，有人把同一付款指令投入两次。邮员规定快速通道只送无副作用的查询，付款必须等待新确认。密封链路要配合正确的目标验证，协议里的提速功能也有适用边界。

## 防御步骤 / 工作流程

1. 默认采用 TLS 1.3；兼容需要时按 RFC 9325 配置 TLS 1.2，移除弃用版本与弱套件。
2. 自动化签发和续期，监控到期与配置漂移；所有客户端强制验证名称与信任链。
3. 检查边缘、负载均衡到应用的完整链路，管理信任代理与转发头，必要时使用内部 TLS/mTLS。
4. 为浏览器配置合适的 HSTS、Secure Cookie 和混合内容策略；先确认全部子域条件再扩大范围。
5. 禁止敏感写操作使用未经防重放设计的 0-RTT，演练证书失效、私钥泄露与续期失败。

## 优缺点分析

TLS 广泛兼容，能抵御链路旁观与篡改。代价是证书、会话恢复和代理部署需要管理；终端或应用被控制后，通道加密无法保护已经交付的明文。TLS 还会隐藏部分内容，使网络检测需结合终端与应用日志。

## 应用场景

网站、API、服务间通信与消息系统都可用 TLS。公网证书和内部 CA 各有管理方式，选择取决于客户端信任与服务身份治理，而不是简单以“内网”为由省略验证。

## 实践建议

上线检查错误域名、过期证书、未知 CA 等拒绝路径，同时测试老客户端兼容性。把续期告警落实到负责人。避免用“HTTPS 全站”代替授权、输入验证、会话安全及供应链检查。
