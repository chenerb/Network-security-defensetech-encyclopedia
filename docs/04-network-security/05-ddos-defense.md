# DDoS 防御：把有限资源留给真实业务

## 概述

CPU 只用了 30%，为什么网站仍打不开？分布式拒绝服务（Distributed Denial of Service，DDoS）通过多来源流量耗尽带宽、连接、计算或应用依赖，破坏可用性。瓶颈可能在上游链路、DNS、负载均衡、数据库或外部接口，而非应用 CPU。

> **教育与防御边界**：本篇仅用于教育学习与合法防御，不提供流量生成、反射放大或攻击代码；容量验证须在获授权的受控环境进行。

## 历史背景

随着互联网公开服务与大量联网设备增长，拒绝服务从单点资源耗尽扩展为多来源流量。2006 年 RFC 4732 系统讨论互联网 DoS 设计问题；更早的 RFC 2827 给出源地址过滤思路。它们是基础架构资料，不是今天某个厂商的容量承诺；现代具体容量应由服务合同与演练验证。

## 核心原理

容量型事件消耗带宽，协议状态型事件消耗连接或设备状态，应用层事件耗尽昂贵查询、缓存、线程或依赖配额。这些类别可以叠加。反射放大的防御包括运营侧源地址验证和避免公开提供不必要的反射服务；受害者不能单靠本机配置消除全网伪造来源。

若流量超过本地接入链路容量，服务器防火墙即使丢弃全部坏包，合法流量也已在上游拥塞，所以需要运营商、清洗服务或边缘网络在拥塞前过滤。内容分发网络（CDN）缓存静态内容，但动态写操作、登录和源站直连仍可能成为瓶颈；源站应限制入口，DNS、备用域名及管理接口也要纳入保护。

应用防御使用分层限速、并发上限、超时、缓存、队列与熔断，把稀缺资源留给关键业务。按 IP 限流会误伤 NAT 后的真实用户，也可能漏掉分散请求，应结合账号、接口、成本与行为。突发热门活动与恶意流量可能相似，判断需结合时间、业务转化、来源变化和依赖指标，不能用“访问量大”单独定性。

> **🧠 费曼自问**：店内保安再快，门外唯一道路堵死时，顾客还能到店吗？

## 通俗解释

DDoS 防御像餐馆管理拥挤：道路堵塞需要交通部门疏导，门口拥挤需要预约，厨房繁忙需要简化菜单和限制昂贵菜品。不断加桌子可能让厨房和账单先垮掉，扩容须匹配所有瓶颈和预算。

## 📖 寓言故事

山村餐馆遇到一场盛会，门口人越来越多，厨师却还有空，因为通村窄桥已经堵满。老板在店门口增加保安无济于事，只好与镇上协调，把队伍在桥前分流。桥通后，少数客人不断点最费时的菜，厨房又被占满。老板启用预订、简化菜单，为老顾客保留有限窗口，并设定每日额外采购预算。盛会结束后，他复盘了桥、门口和厨房的耗时。保护可用性要在真实瓶颈前行动，并以业务恢复而不是拦截数字衡量结果。

## 防御步骤 / 工作流程

1. 盘点公网入口和依赖，建立带宽、包速率、连接数、延迟、错误率及单位请求成本基线。
2. 提前约定上游清洗、边缘接入与 DNS 冗余的启动流程，限制源站只接受可信入口。
3. 对昂贵接口设置分层限速、缓存与并发上限，定义关键业务降级、排队及超时策略。
4. 事件发生时先确认瓶颈与业务影响，联系供应商过滤，保存必要样本并谨慎调整规则。
5. 持续监控误伤、成本和其他安全事件；恢复后分阶段撤销临时规则，复盘容量与响应时间。

## 优缺点分析

边缘与上游防护可抵挡超过单站能力的流量，应用降级可保住核心流程。代价是供应商依赖、持续费用与误伤风险；验证码可能影响无障碍和自动化客户，扩容也可能把攻击转化为高额账单。

## 应用场景

电商、公共查询、游戏、预约与支付服务都需要可用性设计。关键 API 应有独立配额与降级策略，不能因为主页可访问就断言业务已经恢复。

## 实践建议

预先准备联系人、授权范围和费用上限，用离线日志或受控演练验证决策。设置外部可用性探测，检查 DNS 和非 CDN 入口。应急拦截要有期限与恢复条件，黑洞路由可能保护其他网络，却同时放弃被引流目标的可用性。

## 总结

DDoS 防御是瓶颈识别、上游协作与业务韧性的组合。保持合法请求成功、控制成本并可安全恢复，是比“拦截了多少流量”更实用的目标。
